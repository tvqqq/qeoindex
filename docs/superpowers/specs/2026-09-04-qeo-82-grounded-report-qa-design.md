# QEO-82 Grounded Research Report Q&A Design

## 1. Scope

QEO-82 adds server-side question answering over one already-ingested research report. Every answer is grounded only in canonical evidence for the current published revision of that report and returns page-level citations that can later drive QEO-84 PDF navigation.

The service must never use outside knowledge to fill missing report content, never mix evidence from another report or stale report revision, and never expose hidden chain-of-thought, provider credentials, raw provider payloads, or internal prompts.

Out of scope:

- cross-report/global research chat;
- persistent chat history;
- report detail/chat UI;
- OCR/vision fallback;
- AI Council report consumption;
- scheduler/backfill orchestration;
- embeddings/vector retrieval unless later quality measurement proves lexical retrieval insufficient.

## 2. Dependency and evidence identity

QEO-81 owns secure PDF ingestion, page-local chunks, grounded structured analysis, route-aware identity, and atomic publication. QEO-82 consumes only this published research-report evidence boundary.

Retrieval must not filter by `report_id` alone. A report may retain historical `content_hash` and `chunk_version` rows, so QEO-82 resolves one exact current evidence identity before every retrieval:

1. load the report and require `analysis_status = 'ready'` plus a non-null current `content_hash`;
2. load the latest successfully published analysis row for that exact `report_id + content_hash`, ordered by `processed_at desc, created_at desc, id desc`;
3. read that analysis row's `chunk_version`;
4. retrieve chunks only for the exact `report_id + content_hash + chunk_version` identity.

QEO-81 analysis rows represent successfully published analysis bundles; `ready` is a report-level terminal state, not an analysis-row status. This design therefore does not invent an analysis status column.

If the report revision changes between evidence resolution and retrieval, retrieval fails closed rather than falling back to another revision.

The stable server-side entrypoint is:

```ts
answerResearchReportQuestion(
  client,
  input: {
    reportId: string
    question: string
    history?: ResearchReportQaTurn[]
  },
  deps?: ResearchReportQaDependencies,
): Promise<ResearchReportQaResult>
```

The HTTP route is a thin authenticated adapter and never calls OpenAI directly.

## 4. Retrieval strategy

### 4.1 MVP choice

Use PostgreSQL lexical/full-text retrieval over `market_research_report_chunks`.

Reasons:

- deterministic and auditable;
- directly reuses QEO-81 canonical chunks;
- exact page/chunk provenance is straightforward;
- avoids a second embedding/vector lifecycle before retrieval quality is measured.

A future pgvector implementation may replace retrieval internals behind the same interface without changing the grounding contract.

### 4.2 Exact filters

Every retrieval call is constrained by:

- `report_id`;
- current report `content_hash`;
- `chunk_version` from the latest successfully published analysis for that hash.

No cross-report or cross-version fallback is allowed.

### 4.3 Query construction

The lexical query is derived from:

- the current user question;
- a bounded number of recent **user** turns only when they help resolve a follow-up reference.

Assistant history is not evidence and is never inserted into the lexical evidence corpus.

Retrieval returns a bounded ordered list:

```ts
interface ResearchReportQaEvidence {
  evidenceId: string
  chunkId: string
  reportId: string
  contentHash: string
  chunkVersion: string
  page: number
  chunkIndex: number
  content: string
  rank: number
}
```

`evidenceId` is generated by the server from the retrieved row identity and is the only citation identifier the model may reference.

### 4.4 Context budget

The service hard-caps:

- retrieved chunk count;
- total retrieved context characters/tokens;
- history turn count;
- per-turn length;
- question length.

Context selection is deterministic for the same query/evidence inputs. If model context requires truncation, citation validation still checks excerpts against the canonical retrieved chunk content, not against a model-generated reconstruction.

## 5. Pending schema and RPC contract

The QEO-80 research schema remains `QUARANTINED`, so QEO-82 may amend the existing pending migration before production promotion. It must not create an active ALTER migration for a schema that is not production-applied.

Add lexical retrieval support to the existing pending schema:

- full-text search support for `market_research_report_chunks` using a Postgres configuration compatible with Vietnamese/financial text;
- GIN-backed search expression/column;
- service-role retrieval RPC, named canonically in implementation, accepting `report_id`, `content_hash`, `chunk_version`, normalized query text, and a hard result limit;
- RPC returns `id`, `page_number`, `chunk_index`, `content`, `chunk_hash`, `chunk_version`, and lexical rank;
- RPC verifies the requested report still has the supplied current `content_hash` and `analysis_status = 'ready'` before returning evidence;
- result limit is clamped in SQL even if a caller requests more.

Privilege contract:

- route authenticates with `requireApiFeature("research")` first;
- after auth succeeds, server-only service code obtains the existing trusted `getSupabaseServerClient()` service-role client because research-report chunks are shared system evidence, not user-owned rows;
- revoke retrieval RPC execute from `public`, `anon`, and `authenticated`;
- grant execute only to `service_role`;
- browser clients therefore cannot invoke the retrieval RPC directly or choose arbitrary historical versions.

Existing read-only RLS on research tables remains unchanged unless a later UI issue explicitly changes it.

If a generated `tsvector` column is unsuitable in the exact deployment environment, an indexed `to_tsvector(...)` expression is acceptable provided the same exact-version, replay-safe RPC contract is preserved.

## 6. Grounded answer contract

The provider never supplies authoritative page or chunk metadata. The server assigns evidence IDs before the model call.

Provider output:

```ts
interface ResearchReportQaModelOutput {
  status: "answered" | "not_found"
  claims: Array<{
    text: string
    citations: Array<{
      evidenceId: string
      excerpt: string
    }>
  }>
}
```

Validated public output:

```ts
interface ResearchReportQaCitation {
  page: number
  chunkId: string
  excerpt: string
}

interface ResearchReportQaResult {
  reportId: string
  status: "answered" | "not_found"
  answer: string
  citations: ResearchReportQaCitation[]
  audit: ResearchReportQaAudit | null
}
```

`answer` is assembled from validated claims. Page and chunk metadata are projected from the server-side evidence map; model-provided page numbers or chunk IDs are never trusted.

## 7. Citation validation

Validation is fail-closed.

For `answered`:

- at least one claim exists;
- every material claim has at least one citation;
- every `evidenceId` belongs to the exact retrieved evidence set for this request;
- every excerpt is short and textually grounded in the canonical chunk after whitespace normalization;
- duplicate citations are deduplicated by server evidence identity;
- claim text and total answer length are bounded.

For `not_found`:

- claims must be empty;
- citations must be empty;
- service returns a stable user-facing statement equivalent to `không tìm thấy thông tin này trong báo cáo`;
- zero usable retrieval evidence returns `not_found` with zero AI calls.

Malformed JSON, schema failure, or citation-grounding failure gets at most one repair attempt using the exact same immutable evidence set. A second invalid result fails closed.

## 8. Prompt-injection boundary

Retrieved report chunks are untrusted document data. Provider instructions state that evidence text cannot:

- alter the system/developer task;
- authorize tools;
- alter the output schema;
- request outside knowledge;
- override citation rules;
- request hidden reasoning or secrets.

Evidence is serialized as structured data with stable IDs and content. Conversation history is serialized separately. Neither PDF text nor chat history is interpolated into provider instructions.

## 9. Conversation scope

QEO-82 does not persist chat history.

Request history type:

```ts
type ResearchReportQaTurn = {
  role: "user" | "assistant"
  content: string
}
```

Rules:

- only a bounded recent suffix is accepted;
- each turn has a hard character limit;
- history helps resolve follow-up wording only;
- assistant history is never treated as report evidence;
- every answer is freshly grounded against the current report revision.

## 10. AI routing and provider behavior

Reuse generic OpenAI Responses envelope/usage helpers from `modules/ai/openai-response.ts`.

Q&A routing is independently configurable from QEO-81 report analysis so model tuning does not alter the analysis identity. Q&A uses its own environment/runtime keys, prompt version, and model-route key.

Provider requirements:

- Responses API Structured Outputs;
- `store: false`;
- `tools: []`;
- bounded timeout and output budget;
- configurable reasoning effort;
- prompt-cache identity derived from Q&A prompt version plus normalized question/history and immutable evidence identity;
- one bounded incomplete-output retry via the shared helper;
- fallback only for retryable network/429/5xx/provider failures;
- 401/403 fail fast without fallback fan-out;
- one immutable-evidence validation repair attempt, then fail closed.

No hidden chain-of-thought is stored or returned.

## 11. Usage and observability

Return an audit compatible with existing AI usage dimensions:

- requested model;
- actual response model;
- attempted models and fallback flag;
- response ID;
- input/cached/output/reasoning/total tokens;
- latency;
- nullable estimated cost;
- nullable pricing version;
- Q&A prompt version and model-route key.

QEO-82 does not add a persistent chat table or a parallel usage-accounting subsystem. Operational/provider errors exposed to clients are sanitized and bounded. API keys, raw provider bodies, and internal prompts are never returned.

## 12. Authentication and abuse controls

The route calls `requireApiFeature("research")` before any service-role client creation, report retrieval, or provider call.

Request validation includes:

- valid report ID shape;
- non-empty bounded question;
- bounded history count and per-turn size;
- explicit input field limits;
- `Cache-Control: no-store` responses.

The repository currently has no reusable durable per-user rate limiter for this domain. QEO-82 does not introduce an in-memory serverless limiter that would provide misleading protection. Durable rate limiting remains a separate shared capability if later required.

## 13. Error handling

Stable service outcomes:

- `answered`: validated grounded answer;
- `not_found`: report does not support the answer or retrieval has no useful evidence;
- typed service error: invalid request, report unavailable/not ready, service-role configuration unavailable, stale evidence identity, retrieval failure, provider failure, or repeated malformed/ungrounded provider output.

Boundaries:

- missing/not-ready report performs zero AI calls;
- zero evidence performs zero AI calls;
- stale revision fails closed;
- provider failure never mutates QEO-81 report analysis/chunk evidence;
- no partial chat storage can exist because QEO-82 persists no conversations.

## 14. Public module and API boundaries

Expected internal files:

```text
modules/research-reports/qa/
  retrieval.ts
  prompt.ts
  schema.ts
  openai.ts
  service.ts
```

`modules/research-reports/index.ts` exports only stable Q&A service/types needed by API/UI consumers. Prompt, schema, provider, and retrieval internals remain private.

HTTP route:

```text
app/api/research-reports/[id]/chat/route.ts
```

The route:

1. authenticates `research` feature access;
2. validates request fields;
3. obtains trusted server infrastructure only after auth passes;
4. calls the public Q&A service;
5. maps typed outcomes to bounded JSON;
6. returns `no-store`.

## 15. Testing strategy

Implementation is test-first.

Required tests:

1. evidence resolution requires report `ready` plus current content hash;
2. latest successful analysis for exact current hash deterministically supplies `chunk_version`;
3. retrieval filters exact `report_id + content_hash + chunk_version`;
4. historical chunks for the same report are never mixed;
5. another report's chunks are never retrieved;
6. SQL result limit is bounded and lexical ranking deterministic for fixtures;
7. supported fact returns `answered` with correct canonical page/chunk citation;
8. ticker/target-price question cites the page containing the value;
9. unsupported question returns explicit `not_found` without outside knowledge;
10. zero evidence performs zero AI calls;
11. follow-up context helps query resolution but answer citations are freshly grounded;
12. prompt-injection text remains untrusted evidence;
13. un-retrieved evidence ID is rejected;
14. excerpt absent from canonical chunk is rejected;
15. `not_found` with claims/citations is rejected;
16. malformed provider result gets one repair, then fails closed;
17. timeout/429/5xx follows bounded retry/fallback;
18. 401/403 fails fast;
19. API authenticates `research` before service-role access and rejects oversized/malformed input before provider work;
20. API never returns keys, prompts, or raw provider request bodies;
21. pending DB contract proves lexical index/RPC, current-hash guard, SQL limit clamp, and service-role-only execute privilege;
22. AI Council/shared OpenAI regression tests remain green;
23. current/AI/DB suites, lint, typecheck, production build, migration replay, and generated-type verification remain green.

Synthetic repository-safe fixtures are used; copyrighted third-party report content is not committed beyond short test snippets where necessary.

## 16. Acceptance mapping

- Fact + page citation: sections 4, 6, 7; tests 7–8.
- Explicit not-found/no hallucination: section 7; tests 9–10, 15.
- No cross-report/version leakage: sections 2, 4–5; tests 1–6.
- Follow-up context: section 9; test 11.
- Prompt injection: section 8; test 12.
- Timeout/malformed/no-evidence: sections 7, 10, 13; tests 10, 16–18.
- Auth/no secret leakage: sections 5, 11–12, 14; tests 19–21.
